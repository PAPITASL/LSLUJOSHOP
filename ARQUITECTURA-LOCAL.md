# Revisión del proyecto y adaptación

La aplicación es un sitio Django 6.0.7 ejecutado con Python 3.13 de 64 bits. Usa plantillas HTML y Bootstrap 5 con estilos, JavaScript, fuentes Bootstrap Icons y logos locales. No se sustituyeron pantallas ni lógica comercial.

La base real es PostgreSQL 18.4, `lujoshop_db`, en el servicio local `postgresql-x64-18`, puerto 5432. `db.sqlite3` tiene cero bytes y no contiene los datos. Los modelos comerciales usan tablas existentes (`managed=False`); no se ejecutaron migraciones ni se reemplazó la base. Las cuentas y hashes de contraseñas pertenecen al sistema de autenticación de Django. La recuperación conserva todo el esquema y sus datos mediante `pg_dump`/`pg_restore`, sin convertir a SQLite.

Funciones encontradas: productos e inventario, clientes, vendedores, órdenes y detalles, abonos, comisiones, recibos, movimientos, entregas y costos pendientes, referencias BOG, reportes comerciales/financieros y cierres mensuales. `openpyxl` procesa importaciones y plantillas Excel; ReportLab y Pillow generan los PDF y sus gráficos. No hay campos de archivo o imagen persistentes en los modelos ni un almacén MEDIA configurado. Los logos y fotografías actuales están en `static/img`; `artifacts` contiene PDF, imágenes de informes y un archivo histórico JSON. Los Excel importados se procesan desde la solicitud y no se guardan como adjuntos. Los documentos descargados por el usuario fuera del proyecto deben copiarse por separado.

Dependencias de escritorio: pywebview 6.2.1 para la ventana nativa con WebView2; Waitress 3.0.2 para WSGI; WhiteNoise 6.12.0 para los estáticos. Se reutiliza la implementación inicial de `desktop.py`, ampliada con bloqueo, control de PostgreSQL privado, comprobación de carga y registro de errores. `LujoShop.vbs` elige Python portátil cuando está disponible y evita la consola. `Crear acceso directo.cmd` utiliza el logo ICO existente.

`local_runtime.py` controla la exclusión mutua y el ciclo de procesos. En la instalación original se usa el servicio compartido sin detenerlo. En las recuperaciones se inicia un clúster propio con contraseña técnica nueva y puerto libre, limitado a 127.0.0.1; al salir se cierra. Waitress también escucha únicamente en 127.0.0.1. Los procesos no se registran como servicios ni modifican el PostgreSQL original.

`recovery.py` exporta una instantánea PostgreSQL repetible, la comparte con el inventario de verificación, copia código/recursos y herramientas, calcula SHA256 y genera un ZIP con fecha. El archivo `.env` del paquete conserva la clave Django y excluye las credenciales PostgreSQL originales. La restauración rechaza destinos existentes, comprueba todos los hashes antes de copiar, crea un clúster y base nuevos, importa de forma transaccional y compara cantidades y hashes de todas las tablas. Las secuencias y restricciones son restauradas por PostgreSQL, no reconstruidas manualmente.

La única llamada de red funcional encontrada es la consulta opcional de TRM en datos.gov.co. Sin internet falla con un aviso y permite una tasa manual. Los enlaces de documentación en comentarios y el espacio de nombres SVG no son recursos remotos necesarios. No se encontraron CDN en las plantillas. PDF, Excel e inventario no necesitan internet. La impresión se realiza descargando el PDF a un visor instalado en Windows.

Los binarios portátiles de Python y PostgreSQL, bibliotecas, paquetes instalados y licencias disponibles se incluyen en los respaldos. También se incluyen instaladores completos de Microsoft para WebView2 y Visual C++ v14 x64. Windows y .NET Framework 4.8 son requisitos del sistema. No se instalaron ni cambiaron componentes compartidos para hacer esta adaptación.
